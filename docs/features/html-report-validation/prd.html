Know when an HTML report is ready to share

One validation result combines visual, functional, and declared-browser evidence without treating missing checks as success.

Review first

Does this define enough observable evidence for an author to decide whether a generated report is ready to share, without prescribing the validator's implementation?

Moment, friction, and bet

A report can look finished while critical review states remain broken

An author has one self-contained HTML artifact and needs evidence strong enough to make a sharing decision.

Moment
A report author has generated a self-contained HTML document and is preparing to share it with reviewers or stakeholders.
Friction
A report can appear correct in one browser while hiding clipped content, broken navigation, inaccessible controls, missing fallback behavior, or print defects.
Bet
Give the author one validation result that combines visual review, functional checks, and evidence from the declared browser matrix.
Proof
The author can distinguish ready, failed, and incomplete validation without interpreting build logs or assuming that an untested state passed.
Boundary
Validation determines readiness; it does not author, repair, approve, publish, or distribute the report.
Why this matters

A convincing default view is not readiness evidence

Without explicit state and environment evidence, report authors can mistake omissions for success.

  • Visual defects can exist only at narrow, short-height, enlarged-text, or print states.
  • Keyboard, disclosure, internal-navigation, and fallback behavior can fail while the default desktop view looks correct.
  • One browser preview says nothing about a required browser or platform that was never run.
  • Raw logs and silent omissions force the author to infer the aggregate result.
Validation outcome

A report earns an explicit readiness result

The author never infers success from silence, partial execution, or a single browser preview.

  1. Identify the artifact
    Select the finished HTML report and the browser support matrix that applies to it.
  2. Run required checks
    Evaluate visual, functional, fallback, print, and browser states against the same immutable artifact.
  3. Review evidence
    Show every required check as passed, failed, or not run, with context sufficient to reproduce failures.
  4. Decide readiness
    Mark ready only when every mandatory check passes; keep failures and missing checks visible.
Linchpin visual

Evidence flows from one immutable artifact to the sharing decision

  1. The author selects one finished report, establishing the artifact under review.
  2. The validator evaluates all required states and records an explicit outcome for each.
  3. The aggregate result is ready, failed, or incomplete and preserves the supporting evidence.
  4. The result informs—but does not make or approve—the author's sharing decision.

Outcome
The sharing decision is evidence-based and does not imply factual correctness, security, approval, or publication.
  • AC-001A conforming report that passes every mandatory state in the declared matrix is reported as ready.
  • AC-002Clipped content, overlap, unreadable hierarchy, or unintended page-level overflow fails the affected viewport or print state.
  • AC-003Intentional wide figures retain readable text through documented overflow treatment rather than unsafe shrinking.
  • AC-004Status remains understandable without color alone and focus indicators remain visible.
  • AC-005Internal navigation, native disclosures, controls, keyboard focus order, and authored destinations work.
  • AC-006The report loads as a self-contained file without remote fonts, styles, scripts, images, frames, or services.
  • AC-007No-JavaScript, script-stripped, reduced-motion, and print states preserve every primary fact, conclusion, warning, source, and next action.
  • AC-008Each browser result names browser, version, platform, and state; omitted required environments are not run, never passed.
  • AC-009A ready result is impossible while any required check has failed or not run.
  • AC-010A rerun evaluates the current artifact and does not present prior success as evidence for changed HTML.
  • AC-011The final result identifies the artifact, validation time, declared matrix, category outcomes, and unresolved failures or skipped checks.

Smallest useful gate

Validate one finished report before distribution

In scope
One finished self-contained HTML report; visual, functional, accessibility-fallback, print, and declared-browser evidence; a readiness summary with failures and missing checks.
Out of scope
Report generation, content editing, automatic repair, approval workflow, hosting, distribution, factual accuracy, security, privacy, regulatory compliance, and undeclared browser environments.
Outcome-protecting rules

Evidence cannot be implied

  • Every required check exposes passed, failed, or not run.
  • Ready requires all mandatory checks to pass against the same report artifact.
  • A failed result identifies the affected review state and provides reproducible context.
  • A rerun evaluates the current artifact; prior success is not evidence for changed HTML.
  • The validator never claims that content is factually correct, secure, approved, or published.
Observable proof

The author can make a defensible sharing decision

  • A complete passing result is visibly ready.
  • A visual or functional defect is visibly failed and names its affected state.
  • A missing required browser result is visibly incomplete and cannot be mistaken for ready.
  • The summary and each category expose enough evidence to explain the aggregate state.
  • The result is explicitly evidence about readiness, not approval or broader assurance.
