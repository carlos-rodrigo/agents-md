Teach System Diagram four explanatory grammars without changing its style

PRD and Design Solution decide when and what a situation needs to illustrate; System Diagram generates sequence, flow, architecture, or component diagrams in the established infrastructure visual language without inventing meaning.

Confirm that capability selection, authority boundaries, staged delivery, sequence limits, and observable acceptance fully express the approved direction; then explicitly approve or request changes to the complete PRD.

Product

Owning document skills can request the right explanatory figure

The product change expands one existing skill rather than creating competing diagram tools or styles.

For a PRD or Design Solution that needs to explain an evidence-backed situation during document review, the product will generate the appropriate sequence, flow, architecture, or component diagram through the existing System Diagram skill, resulting in a deterministic figure that a reviewer can retell; it will not transfer product or architecture authority to the renderer or introduce another visual language.

Why

One generic graph contract cannot teach every requested situation

The current skill is dependable but its source model is limited to manually positioned generic graph elements.

Sourced fact
skills/system-diagram/scripts/diagram-spec.mjs accepts rectangular nodes, groups, and explicitly routed orthogonal edges.
Sourced fact
skills/system-diagram/references/diagram-modes.md classifies semantic questions but does not define participant lifelines, flow decisions/merges, architecture levels, or component interfaces.
Consequence
Temporal interaction must be approximated as a generic graph, while flow, architecture, and component authors must manually recreate conventions that the skill should know.
Plausible drawing is not enough

Without typed semantics and selection guidance, a diagram may look consistent while answering the wrong question or implying unsupported product or architecture truth.

Behavior

The owning skill chooses the question; System Diagram generates the explanation

Approved product truth — Carlos Rodrigo approved that selection follows the situation being explained, while domain authority remains with PRD or Design Solution.

  1. Own the situation
    PRD or Design Solution states the question, evidence, scope, main path, uncertainty, and product or architecture meaning.
  2. Select the capability
    The owning skill chooses sequence for temporal communication, flow for progression and branching, architecture for static bounded communication, or component for decomposition of one scope.
  3. Validate the brief
    System Diagram rejects missing evidence, unsupported semantics, invalid references, excessive complexity, or a brief that needs splitting.
  4. Generate in one style
    System Diagram applies the selected grammar and emits deterministic source/SVG using the existing infrastructure-v1 language.
  5. Embed without reinterpretation
    HTML Report Designer verifies provenance and embeds the figure with the owning document's walkthrough.
  • PRD uses diagrams to explain actor-visible product behavior and never introduces architecture.
  • Design Solution uses diagrams to explain approved boundaries, state, communication, recovery, or decomposition.
  • System Diagram owns generation mechanics and the established style, never product or architecture truth.
  • HTML Report Designer validates and embeds; it does not choose a capability or redraw the figure.
  • Existing system-diagram-v1 sources and generated SVGs remain valid and visually unchanged.
  • Unsupported or crowded meaning returns an actionable blocker instead of a plausible approximation or smaller text.
Product flow

Authority stays with the document while generation becomes capability-aware

Approved product truth — the owning document supplies meaning, System Diagram validates and generates, and unsupported meaning returns for refinement.

  1. PRD or Design Solution identifies a situation that needs explanation and owns its product or architecture meaning.
  2. The owning skill supplies a bounded evidence-backed brief and selects sequence, flow, architecture, or component from the explanatory question.
  3. System Diagram validates evidence, semantics, limits, and uncertainty without adding unsupported truth.
  4. Supported meaning becomes deterministic infrastructure-v1 SVG; ambiguous or excessive meaning returns for refinement or splitting.
  5. HTML Report Designer verifies and embeds the figure so the reviewer can retell the situation.

System workflow

Order the interaction

  1. 01

    Order the interaction

    Input
    A supported temporal brief is complete and source ordered.
    Action
    System Diagram maps participants, events, activations, and fragments to the sequence grammar.
    Handoff
    A deterministic lifeline figure preserves the approved order and style.
    Result

  • AC-004Sequence output preserves one to eight participants and one to forty-eight messages in source order, with no more than sixty-four total events.
  • AC-005The capability represents synchronous, asynchronous, return, and self messages plus notes, explicit activations, and bounded alt, opt, and loop fragments when supplied.
  • AC-006The approved envelope allows at most sixteen notes, twelve fragments at depth three, and sixteen activations at simultaneous depth three; exceeding it fails with split guidance.
  • AC-007Sequence output uses the established infrastructure-v1 visual language and does not change byte-current v1 fixtures.
