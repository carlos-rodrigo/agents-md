Architecture pressure

Temporal semantics must be added without destabilizing a trusted renderer

The current path is deterministic and portable, but it is structurally a manually positioned graph renderer.

Sourced fact
diagram-spec.mjs exposes SCHEMA_VERSION system-diagram-v1 and accepts only positioned groups, nodes, and orthogonal edges.
Sourced fact
render-system-diagram.mjs embeds the complete infrastructure-diagram.css file and fixed v1 metadata into every SVG, so changing that bundle changes retained output bytes.
Sourced fact
canonical-report.mjs accepts only system-diagram-v1 nodes and edges and invokes one hard-coded renderer for exact-output verification.
Sequence pressure
Lifelines, temporal event order, returns, self messages, activations, notes, and fragments cannot be represented truthfully as generic graph adjacency.
Compatibility pressure
Existing fixtures, exported SCHEMA_VERSION and normalizeSpec behavior, report embeddings, and copied-skill rendering already depend on the current v1 path.
Portability pressure
The new path must remain dependency-free under actual Node 18 and current Node execution, not merely the developer's active process version.
A shared rewrite is the risky obvious solution

Routing v1 through a new scene model or modifying its embedded CSS would make byte preservation depend on a broad refactor before sequence generation proves any reusable abstraction.

Future capabilities
Flow, architecture view, and component decomposition add bounded contracts only after accepted examples prove their needs; they do not force a shared v2 graph engine into this slice.
  • Top-level fields are exactly schemaVersion, diagramType, layoutVersion, mode, id, title, desc, optional reviewPrefix, participants, events, and activations. Authored coordinates, colors, CSS, fonts, icons, URLs, and arbitrary SVG are rejected.
  • schemaVersion, diagramType, and layoutVersion are fixed to system-diagram-v2, sequence, and sequence-v1. Mode is exactly component-communication, causal-code-flow, or outside-in-slice; mode remains the semantic question while diagramType is only the rendering grammar.
  • A participant contains exactly id, kind, and label. Kind is actor, external, system, service, or store; participant array order is authoritative.
  • A message contains exactly id, type message, messageType, from, to, label, kind, and replyTo only for return. messageType is sync, async, return, or self; kind is primary, secondary, success, warning, or risk.
  • Self requires identical endpoints. Other messages require distinct endpoints. Return requires replyTo naming an earlier message with reversed endpoints; replyTo is rejected for sync, async, and self.
  • A note contains exactly id, type note, text, kind, and exactly one participant or event anchor naming an existing element. Kind uses the same semantic enum as messages.
  • A fragment contains exactly id, type fragment, fragmentType, label, kind, and branches. A branch contains exactly id, label, and events. Alt has two to four non-empty labelled branches; opt and loop have exactly one non-empty labelled branch.
  • An activation contains exactly id, participant, startEvent, and endEvent. Both endpoints name messages involving that participant, start precedes end, and both belong to the same event container or fragment branch.
  • Every participant, event, branch, and activation ID is globally unique lowercase kebab text. Recursive event order and branch order are authoritative; omitted or unsupported fields never receive semantic defaults.
  • reviewPrefix is optional lowercase dot and kebab text. Output review IDs combine reviewPrefix, diagram id, element role, and element id; no author-supplied per-element review override is accepted in the initial contract.

Key flows

Source meaning becomes geometry only after strict semantic validation

The success, compatibility, and recovery flows share provenance checks but not normalization code.

  1. Select
    The owning PRD or Design Solution matches a temporal communication question to sequence and retains its source-classified brief.
  2. Preflight
    The sequence renderer rejects raw input over 64 KiB before JSON parsing, then rejects unknown fields and invalid XML text.
  3. Validate
    The v2 validator resolves participants, recursively counts events and fragments, validates references and branch rules, and returns normalized semantic data or one actionable error.
  4. Lay out
    sequence-v1 measures text conservatively, sizes participant headers, expands lane gaps for labels, notes, and self messages, assigns one row per ordered event, encloses fragments, and places activation rails.
  5. Render
    The sequence serializer escapes all text and emits source digest, version metadata, stable IDs, title and description, lifelines, messages, fragments, labels, and renderer-owned reveal groups.
  6. Verify and embed
    HTML Report Designer reads allowlisted root markers, enforces the v2 pre-parse size cap, confirms parsed source and marker agreement, invokes the matching exact renderer, verifies self-containment and infrastructure-v1 metadata, then embeds SVG beside the source-owned walkthrough.
  7. Recover
    Invalid references, excessive dimensions, collisions, or unsupported topology stop before output; the owning skill refines or splits the brief and reruns the same path.
Measurement
Count Unicode code points with one font em per non-space and one-half em per whitespace, round upward to integer units, wrap greedily at whitespace then by code point, and reject authored line breaks. This deliberately overestimates system-font text.
Horizontal order
Place participant headers in source order at 96px height. Initialize each adjacent lane gap to at least 220px and enough for half-header widths plus 48px clearance.
Horizontal expansion
Process events once in source order. A label, note, or 96px self-message gutter may only increase crossed lane gaps; divide any deficit evenly and assign remainder units to the earliest gaps.
Vertical order
Start events 64px below headers. Messages use 72px rows; note rows use at least 72px; fragment height is its 40px band plus ordered branch content, 24px separators, and 24px bottom clearance.
Fragments and activations
Stack fragment branches and nested events in source order. Activation rails are 12px wide at the participant center; concurrent depth offsets eight units to the right and never exceeds three.
Bounds
Extend lifelines 48px below the final event, add 48px outer padding, then reject any viewBox or SVG above the approved cap. No later pass compacts or reorders geometry.
V1 compatibility flow
system-diagram-v1 continues through the existing renderer and exact report verifier; no v2 normalizer, layout, CSS extension, or metadata touches it.
Sequence success flow
Valid semantic source produces one byte-deterministic SVG and a report that preserves existing visual and walkthrough behavior.
Source failure flow
The first failing contract rule returns its stable field and event context; no partial SVG is written.
Tamper or staleness
A changed JSON digest, modified SVG, wrong renderer metadata, executable content, or unsupported version fails report rendering before HTML output.
Dimension recovery
Layout expands lanes and rows until the approved viewBox cap; it never reorders participants or events or shrinks below established text sizes, and asks for a split when the cap cannot hold the brief.
Architecture path

The source-version seam isolates compatibility from new temporal layout

The current v1 renderer and the proposed sequence v2 pipeline converge only at version-aware report verification.

  1. PRD or Design Solution supplies an approved question and evidence-backed semantics.
  2. The retained source contract routes before normalization or rendering.
  3. System-diagram-v1 remains on its current validator, CSS, metadata, and renderer path.
  4. Sequence v2 passes through strict references and limits, then one source-ordered integer layout and an additive same-style SVG serializer.
  5. Invalid sequence source returns an exact blocker before geometry; valid v1 or v2 output reaches the matching report verifier.
  6. The canonical report embeds byte-current SVG with its source-owned walkthrough, preserving one visual language for the reviewer.

Constraints and approval proof

Implementation planning is credible only with exact limits and observable gates

The sequence slice must prove compatibility, semantics, deterministic geometry, portability, security, accessibility, and report integration together.

Source
64 KiB raw JSON before parse; strict unknown-field rejection; IDs at most 64 characters; title 120; description 600.
Participants and events
1–8 participants; 1–48 messages; at most 64 recursive events total, counting every message, note, and fragment wrapper but not branch containers.
Notes and fragments
At most 16 notes; 12 fragments; three fragment ancestors; alt has 2–4 branches; opt and loop have exactly 1; every branch contains at least one event.
Activations
At most 16 spans; simultaneous depth three per participant; ordered endpoints in one event container or branch.
Text
Participant labels use 64 characters and 3 lines; message and fragment labels use 120 characters and 2 lines; note text uses 300 characters and 5 lines; authored text remains at least 14px.
Geometry
Integer coordinates; source order is the only tie-breaker; no authored coordinates, randomness, optimization, or iterative pass; viewBox at most 4096 × 8192.
Output
At most 1 MiB SVG; source SHA-256; explicit data-diagram-schema, data-diagram-type, data-layout-version, renderer, and infrastructure-v1 style metadata; stable review IDs; searchable escaped text; title and description; role img; and no remote or executable content.
Font guarantee
A versioned conservative code-point width table owns wrapping and geometry; bytes are cross-machine deterministic, while system-font glyph rasterization is not claimed pixel-identical.
  • DA-001 — Every retained v1 fixture and canonical report remains byte-identical; SCHEMA_VERSION, normalizeSpec, review-ID helpers, current CLI behavior covered by tests, metadata, and infrastructure-diagram.css remain compatible.
  • DA-002 — A minimal sequence fixture and a consequential failure and recovery fixture render participants; sync, async, return, and self messages; notes; activations; and alt, opt, and loop fragments in exact source order.
  • DA-003 — Focused invalid fixtures prove each unknown field, limit, duplicate ID, missing reference, return mismatch, fragment rule, activation crossing, source-size, dimension, and output-size failure with stable contextual errors.
  • DA-004 — Repeated rendering and --check produce identical bytes under actual Node 18 and the current project Node from the repository and from an allowlisted copied skill that excludes node_modules and external package resolution.
  • DA-005 — Canonical reports accept exact v1 and sequence-v2 output, reject stale, tampered, or mismatched renderer output, preserve report-owned walkthroughs, and keep canonical-report-v1 source compatibility.
  • DA-006 — Desktop, 320px local overflow, no-JS, reduced-motion, and print checks prove readable text, visible complete static content, no clipping, and no collisions among nodes, headers, messages, labels, fragments, or activations using SVG geometry assertions.
  • DA-007 — Hostile labels render only as escaped text; executable or foreign content, external assets, XML-invalid controls, arbitrary style, and oversized input or output fail before report output.
  • DA-008 — PRD, Design Solution, and System Diagram guidance plus behavioral evals select sequence only for participant and time interaction and return ambiguous, merely linear, static topology, and one-scope decomposition requests to their proper capability.

Meaningful boundary

Sequence proves the extension seam; later grammars remain deliberately unbuilt

This design authorizes no generic graph engine, migration, or implementation planning for flow, architecture, or component diagrams.

  • Unchanged: product and architecture authority, report-owned walkthroughs, canonical diagram block shape, Editorial Infrastructure reports, infrastructure-v1 visual language, and all current v1 retained sources.
  • Immediate design scope: capability-selection guidance and evals, strict sequence-v2 source, sequence-v1 direct layout, additive sequence SVG components, exact report verification, fixtures, and proof gates for PRD AC-001 through AC-007.
  • Deferred: flow AC-008–010, architecture-view AC-011–013, and component-decomposition AC-014–016 until real examples choose the next vertical slice and an approved design amendment defines its contract.
  • Excluded: shared scene IR, automatic graph optimization, force layout, generic migration, authored styling, remote assets, alternate renderer, derived report walkthroughs, class diagrams, timing diagrams, deployment views, and task creation inside this design.
  • ADR consequence: after explicit design approval, amend docs/adrs/architecture.md to preserve the accepted version-isolation, same-style extension, and report-verification rationale before tasks become executable.
