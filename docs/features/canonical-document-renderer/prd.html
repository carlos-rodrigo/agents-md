Canonical reportEditorial Infrastructure
Review Product requirements Updated 2026-08-03

Make every durable report look and behave like the same product

PRDs, designs, reports, decisions, research briefs, and diagram packets use one canonical report experience, explicit decision recording, and evidence-backed infrastructure-style SVG figures.

Review first

Confirm that one rendering boundary and the globally approved Editorial Infrastructure language preserve domain-owned meaning while removing template and diagram ambiguity.

Product

Reviewers get one dependable document experience

The product is the review experience, not a collection of loosely synchronized templates.

Actor
A human reviewing an agent-generated durable document
Job and moment
Understand, discuss, and approve product or architecture truth in a browser
Capability
Read one consistent report, inspect a clean infrastructure explanation, and record real decisions
Entry
Open a generated PRD, design, report, decision, research, or diagram HTML artifact
Result
The reviewer can retell the outcome, reference stable anchors, and export decision input
Boundary
The report does not decide product truth, architecture, or approval on the reviewer's behalf
Why

Parallel templates made the review experience untrustworthy

Different report paths drifted in style, component availability, navigation, motion, decision state, and diagram generation.

Agents could select or imitate a PRD, design, generic report, or diagram shell rather than using one enforced report system. A generated document could therefore satisfy content instructions while visibly diverging from the expected template.

Review confidence breaks

A reviewer cannot know whether missing controls, inconsistent diagrams, or apparent decision state reflects product truth or generation drift.

Observed
A newly generated design did not follow the defined report template.
Repository evidence
Separate PRD, design, report, and diagram templates and CSS families existed.
Expected outcome
Every new durable artifact uses one recognizable shell and interaction contract.
Behavior

Meaning is composed first and rendered once

Domain skills decide required content; shared rendering and diagram skills provide consistent presentation.

  1. Compose domain truth
    PRD or Design Solution creates required sourced sections and decision lifecycle without authoring HTML.
  2. Explain one system question
    System Diagram produces an evidence-backed accessible infrastructure SVG.
  3. Render one report
    HTML Report Designer validates structured input and fills one canonical template.
  4. Review and record
    The human reads consistent navigation, records complete decision input, and exports Markdown.
  5. Reconcile explicit approval
    An agent updates canonical source only after the human explicitly approves the product or architecture choice.
  • New reports never select a document-specific shell or style family.
  • Every substantive PRD and durable design contains exactly one evidence-backed infrastructure-style System Diagram.
  • A decision cannot be recorded until option, rationale, and owner are present.
  • Browser-local state and exports never imply canonical approval.
  • Missing companion renderers block generation rather than trigger a lower-quality fallback.
Product flow

Review input becomes canonical truth only through explicit approval

The diagram separates report consistency, local recording, and human governance.

  1. The reviewer asks for a PRD or design based on approved evidence.
  2. The owning skill composes required meaning and gives System Diagram a bounded question.
  3. One report presents that content and its decision controls consistently.
  4. The reviewer records and exports complete review input.
  5. Only explicit human approval updates canonical truth; incomplete input remains open.
Product slices

Three outcomes make the review system dependable

slice-001Render every durable document consistently

A reviewer sees one canonical shell, style, navigation, and component language regardless of document kind.

Boundary: The renderer does not choose or reorder product and architecture content.

story-001 · Feature: a document reviewer can open any durable agent-generated report in one consistent experience; outcome: format drift does not obscure the document's meaning.

Scenario: Canonical generation

Givenan owning skill has complete validated structured content

Whenit invokes HTML Report Designer

Thenone portable report template produces self-contained HTML with actual-section navigation and stable review anchors

Scenario: Renderer unavailable

Giventhe canonical renderer cannot be loaded

Whenthe agent attempts final report generation

Thengeneration blocks with a setup instruction instead of producing a substitute shell

System workflow

Supply meaning→Open report

  1. 01

    Supply meaning

    Input
    The owning skill has approved or clearly proposed content.
    Action
    It writes a structured DocumentSpec.
    Handoff
    The profile validator confirms required roles and lifecycle.
    Result
    The content is ready for canonical rendering.
  2. 02

    Open report

    Input
    The renderer emits self-contained HTML.
    Action
    The reviewer opens it in a browser.
    Handoff
    The same report shell, navigation, components, and fallbacks appear.
    Result
    The reviewer can focus on meaning rather than generation variance.
  • AC-001Only one production report template and CSS source exist.
  • AC-002PRD, design, report, research, decision, and diagram kinds render through the same boundary.
  • AC-003Reports remain readable at 320px, without JavaScript, under reduced motion, and in print.

After this slice, reviewers recognize every durable document as the same report product.

slice-002Record decisions without implying approval

A reviewer can select, explain, record, restore, and export a real decision.

Boundary: Recording does not mutate source or change document status to Approved.

story-002 · Feature: a product or architecture reviewer can leave a complete portable decision record; outcome: an agent can reconcile the exact choice after explicit approval.

Scenario: Complete review record

Givena report contains an open or proposed decision

Whenthe reviewer selects an option, provides rationale and owner, and checks Decision recorded

Thenthe report persists and exports the stable decision record as review input

Scenario: Incomplete review record

Givenselection, rationale, or owner is missing

Whenthe reviewer reaches the recording control

Thenthe checkbox remains unavailable and identifies the missing work

Product-visible workflow

Choose and explain→Record and export

  1. 01

    Choose and explain

    Input
    The decision shows concrete options and a custom path.
    Action
    The reviewer selects and adds rationale and owner.
    Handoff
    The record becomes eligible for completion.
    Result
    The choice is explicit and attributable.
  2. 02

    Record and export

    Input
    Required decision input is complete.
    Action
    The reviewer checks Decision recorded and downloads Markdown.
    Handoff
    The report confirms local persistence and labels the export as review input.
    Result
    The exact stable ID can be reconciled after approval.
  • AC-004Every decision renders a Decision recorded checkbox.
  • AC-005Recorded option, rationale, owner, date, and status survive reload and appear in export.
  • AC-006Accepted decisions require explicit approver/date in canonical source.
After this slice

After this slice, reviewers can leave durable decision input without accidentally approving canonical truth.

slice-003Use one infrastructure visual language for every system diagram

PRD and design diagrams have one evidence, accessibility, visual, and regeneration contract.

Boundary: The report renderer embeds figures but does not invent or redraw system semantics.

story-003 · Feature: a technical or product reviewer can follow one clear evidence-backed system path; outcome: the diagram teaches rather than decorating the report.

Scenario: Consistent explanatory figure

Giventhe owning skill names a diagram question and source-classified semantics

WhenSystem Diagram renders the figure

Thenthe report shows searchable accessible infrastructure SVG with a clear primary route, explicit boundaries, semantic exceptions, and a text walkthrough

Scenario: Inconsistent visual language

Givena figure uses hand-drawn or scene-local styling

Whenthe canonical report attempts to include it

Thengeneration rejects it instead of mixing diagram styles

System workflow

Define brief→Validate semantics→Render and embed

  1. 01

    Define brief

    Input
    A substantive PRD or durable design requires one diagram.
    Action
    The owning skill supplies one question, boundary, and source-classified evidence.
    Handoff
    System Diagram receives one bounded brief instead of an open-ended drawing request.
    Result
    The semantic validation input is explicit.
  2. 02

    Validate semantics

    Input
    System Diagram has the bounded brief.
    Action
    It validates evidence, ownership, labels, route, accessibility text, and scene constraints.
    Handoff
    Invalid semantics stop; valid meaning becomes a deterministic system-diagram-v1 scene.
    Result
    A validated scene is handed to the renderer.
  3. 03

    Render and embed

    Input
    A validated system-diagram-v1 scene is available.
    Action
    System Diagram generates SVG and the report verifies provenance before embedding it.
    Handoff
    The report presents one accessible figure and its ordered walkthrough.
    Result
    The reviewer receives one legible explanatory figure.
  • AC-007Every substantive PRD and durable design has exactly one consistent infrastructure-style System Diagram.
  • AC-008Hand-drawn or scene-local visual variants are rejected.
  • AC-009The same diagram remains understandable in desktop, narrow, no-JS, reduced-motion, and print review.
After this slice

After this slice, every system diagram follows one teachable infrastructure visual language.
