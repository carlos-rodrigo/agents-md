Accept an order once, then deliver it safely

The application seam owns idempotency and commits the order with its fulfillment intent.

Product authority: durable order receipt PRD

  • Product promiseDuplicate client retries create one accepted order and one fulfillment intent.
  • Observable proofThe same request key always returns the same order number.
  • BoundaryPayment capture and fulfillment policy do not change.

Acknowledgement cannot outrun durability

The API must survive retries and process failure without creating a second order or losing the asynchronous handoff.

One application transaction owns both facts

The order application service sees the request key, order state, and outbox write, making it the smallest boundary that can commit them atomically.

Causal system path

The response follows one durable transaction

  1. Route. POST /orders validates the idempotency key and request shape.
  2. Application seam. AcceptOrder loads or creates the request-key record.
  3. Transaction. The seam writes the order, stable response, and outbox intent together.
  4. Result. The API returns the durable order number; the worker later claims the outbox intent.

Architecture decision

Own idempotency at the application transaction

The route lacks persistence ownership; the worker runs too late. The application seam can make acceptance and handoff one fact.

Cost
An idempotency record and outbox row per accepted request.
Benefit
Retries and crash recovery share one source of truth.

Operational risk

A stuck worker must be distinguishable from an empty queue. Track oldest unclaimed intent, retry count, and terminal dispatch failure; rollback leaves committed orders inspectable.

Outside-in delivery slice

  1. Prove duplicate HTTP requests return one order.
  2. Commit order and outbox intent in one transaction.
  3. Prove a worker crash leaves a reclaimable intent.

Intentionally unchanged

Provider selection, payment capture, fulfillment policy, and notification copy remain outside this architecture decision.

Proof strategy

Duplicate and crash paths converge

  • Two concurrent requests with one key return one order ID.
  • A forced transaction failure leaves neither order nor outbox intent.
  • A worker restart claims the existing intent without a second order.
