Let the UI claim success only after durable save

One application seam separates optimistic acknowledgement from the saved state the interface can trust.

Product authority: durable save-state PRD

  • Product promiseThe user sees saving, saved, or recoverable failure without a false confirmation.
  • Observable proofThe saved state appears only after durable evidence returns.
  • BoundaryThe design does not change form fields or downstream processing.

Fast feedback and durable truth arrive at different times

The browser can acknowledge an action immediately, but only the backend transaction can establish the state that survives refresh and retry.

The save use case owns the transition

The use case returns an explicit durable result; transport and UI map it into visible states without guessing from request completion.

Causal system path

One result crosses the UI/backend boundary

  1. Action. The form enters saving state and sends the command.
  2. Route. The endpoint validates transport shape and calls the save use case.
  3. Commit. The use case applies policy and waits for the repository transaction.
  4. Visible result. Durable success maps to saved; a recoverable failure maps to retry without discarding input.
  1. The form owns immediate saving feedback and preserves user input.
  2. The route crosses transport but does not infer durability.
  3. The use case maps repository commit or failure into the only results the UI may render.

Ownership stays narrow

Form
Draft input, saving state, retry affordance.
Route
Transport validation and status mapping.
Save use case
Policy, transaction coordination, durable result.
Repository
Atomic state write and storage errors.
Architecture decision

Return a typed durable result

The UI must never derive saved state from HTTP completion alone.

Cost: explicit result mapping. Benefit: refresh, retry, and failure states share one source of truth.

Interface consequence

The form state model is idle → saving → saved or recoverable failure. Retry preserves fields; saved is terminal for the submitted revision.

Risk: stale responses

Tag each submission revision so a slow earlier response cannot overwrite a newer draft or result.

Intentionally unchanged

Form layout, field validation copy, and downstream processing remain product-owned and outside this seam decision.

Proof strategy

Visible state follows durable evidence

  • A delayed commit keeps the UI in saving, then shows saved after success.
  • A forced storage failure preserves input and exposes retry.
  • An earlier slow response cannot replace the latest revision state.
